# Pheme VA Development HTTP Server

This crate is the development HTTP host for the Pheme VA Rust core. It loads a local Whisper model, exposes transcription and deterministic incident analysis, and can drain in-memory metrics for an external exporter.

This is not yet the production incident API. It does not currently provide persistent logs, incident storage, sessions, confirmation, emergency dispatch, or automatic forwarding to the Go backend.

## Current endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health` | HTTP liveness check |
| `GET` | `/ready` | Transcription runtime readiness check |
| `POST` | `/v1/transcribe` | Transcribe one complete WAV request |
| `POST` | `/v1/analyze` | Extract incident fields from text |
| `GET` | `/v1/metrics/batches` | Drain buffered metric batches |

These are Rust-server routes. They are separate from the Go API routes under `/api/v1/...`.

## Running the server

Run commands from `pheme-va/`. The server requires the `whisper` Cargo feature and a local Whisper model:

```bash
cargo run --release -p server --features whisper -- \
  --model models/whisper/ggml-large-v3-turbo.bin \
  --bind 127.0.0.1:8000 \
  --max-seconds 120
```

The model is loaded before the HTTP listener starts. A missing or invalid model, an invalid bind address, or a build without Whisper support causes startup to fail; it does not produce an HTTP error response.

### Command-line options

| Option | Default / source | Description |
| --- | --- | --- |
| `--model PATH` | Required; `PHEME_VA_WHISPER_MODEL` is supported | Whisper model path |
| `--bind ADDRESS` | `127.0.0.1:8000` | HTTP listen address |
| `--max-seconds N` | `120` | Maximum original WAV duration |
| `--language LANG` | Automatic detection | Optional transcription language |
| `--dictionary TERM,...` | Empty | Comma-delimited dictionary terms |
| `--metrics-enabled` | `false`; `PHEME_VA_METRICS_ENABLED` | Enable metric events |
| `--incident-metrics` | `false`; `PHEME_VA_INCIDENT_METRICS` | Enable incident-only metrics by default |
| `--resource-sampling` | `false`; `PHEME_VA_RESOURCE_SAMPLING` | Enable CPU/RAM/device sampling |

For example:

```bash
cargo run --release -p server --features whisper -- \
  --model models/whisper/ggml-large-v3-turbo.bin \
  --language en \
  --dictionary 'KLASS,whisper.cpp,west entrance' \
  --metrics-enabled \
  --resource-sampling
```

The default bind address is loopback. The server currently provides no authentication, TLS, CORS, rate limiting, or production security boundary.

## Common error response

Errors generated by the server handlers use this shape:

```json
{
  "error": {
    "code": "runtime_unavailable",
    "message": "Analysis runtime is unavailable."
  }
}
```

Unknown routes, unsupported methods, and JSON extraction failures from Axum use Axum's default responses instead of this custom envelope.

## `GET /health`

A liveness check. It does not inspect the model or transcription engine.

### Request

```bash
curl -i http://127.0.0.1:8000/health
```

### Response: `200 OK`

```json
{
  "status": "ok"
}
```

## `GET /ready`

Checks whether the in-process transcription engine reports itself ready.

### Request

```bash
curl -i http://127.0.0.1:8000/ready
```

### Ready response: `200 OK`

```json
{
  "status": "ready"
}
```

### Unavailable response: `503 Service Unavailable`

```json
{
  "error": {
    "code": "runtime_unavailable",
    "message": "Analysis runtime is unavailable."
  }
}
```

With the current Whisper implementation, a successfully loaded model reports ready. Model-load failures happen before the server starts, so they cannot be observed through `/ready`.

## `POST /v1/transcribe`

Transcribes one complete WAV file. The request body is the raw WAV file, not JSON and not a multipart upload.

### Request

```bash
curl -i -X POST http://127.0.0.1:8000/v1/transcribe \
  -H 'Content-Type: audio/wav' \
  --data-binary @recording.wav
```

Accepted media types are:

- `audio/wav`
- `audio/x-wav`

Media-type parameters are tolerated, so `audio/wav; charset=binary` is accepted. The body must be a valid WAV container; bare PCM bytes are not accepted.

The core supports 8-, 16-, 24-, and 32-bit integer WAV input and 32-bit floating-point WAV input. The input may use different sample rates and channel counts. It is downmixed to mono and resampled to 16 kHz before transcription.

`--max-seconds` applies to the original WAV duration. There is no per-request duration override.

### Response: `200 OK`

The response is an unwrapped `TranscriptionResult`:

```json
{
  "status": "Speech",
  "raw_text": "vehicle collided near the west entrance",
  "text": "Vehicle collided near the west entrance",
  "language": "en",
  "model_id": "models/whisper/ggml-large-v3-turbo.bin",
  "model_family": "whisper",
  "model_revision": null,
  "segments": [
    {
      "start_ms": 0,
      "end_ms": 1840,
      "text": "vehicle collided near the west entrance",
      "no_speech_probability": 0.02
    }
  ],
  "gate": {
    "decision": "SpeechDetected",
    "peak_rms": 0.12,
    "peak_amplitude": 0.74,
    "window_count": 92,
    "speech_window_count": 61,
    "max_consecutive_speech_windows": 37
  },
  "dictionary_prompt": null,
  "stt_backend": "models/whisper/ggml-large-v3-turbo.bin",
  "cleanup_backend": "rule-based-formatter",
  "cleanup_status": "Applied",
  "recovery_attempted": false,
  "processing_time_ms": 742
}
```

| Field | Description |
| --- | --- |
| `status` | Final transcript state |
| `raw_text` | Normalized recognizer output before cleanup |
| `text` | Final returned transcript |
| `language` | Detected or configured language, if available |
| `model_id` | Current server wiring reports the supplied model path |
| `model_family` | Currently `whisper` |
| `model_revision` | Optional model revision; normally `null` for this server |
| `segments` | Recognizer segments with millisecond timestamps |
| `gate` | Speech-gate decision and energy statistics |
| `dictionary_prompt` | Prompt generated from configured dictionary terms, or `null` |
| `stt_backend` | Current transcription backend identifier |
| `cleanup_backend` | Text cleanup implementation, if configured |
| `cleanup_status` | Cleanup result |
| `recovery_attempted` | Whether dictionary-prompt recovery was attempted |
| `processing_time_ms` | End-to-end core processing time |

The response enums use Rust variant casing because they are serialized without a rename rule:

- `status`: `Speech`, `NoSpeech`, `InsufficientSpeech`, `DictionaryPromptEcho`, `KnownSilenceMarker`, or `EmptyTranscript`
- `gate.decision`: `SpeechDetected`, `Silence`, `InsufficientSpeech`, or `Unavailable`
- `cleanup_status`: `Disabled`, `NotConfigured`, `Applied`, or `FallbackToRaw`

Valid silent or insufficient-speech WAV files still return `200 OK`. For example, a silent file may return `status: "NoSpeech"`, empty text, and `gate.decision: "Silence"`. These are processing results, not HTTP errors.

### Transcription errors

| Condition | Status | Error code |
| --- | ---: | --- |
| Missing or unsupported content type | `415` | `unsupported_media_type` |
| Empty request body | `400` | `invalid_request` |
| WAV exceeds `--max-seconds` | `400` | `audio_too_long` |
| Runtime is unavailable | `503` | `runtime_unavailable` |
| Invalid WAV, unsupported WAV data, backend failure, poisoned engine lock, or task failure | `500` | `transcription_failed` |

Example:

```json
{
  "error": {
    "code": "audio_too_long",
    "message": "Audio exceeds the configured duration limit."
  }
}
```

Malformed or unsupported WAV data currently maps to the generic `500 transcription_failed` response rather than a structured `400` response.

### Browser upload

A browser can send a selected WAV file directly:

```ts
const file = fileInput.files?.[0];

const response = await fetch("http://127.0.0.1:8000/v1/transcribe", {
  method: "POST",
  headers: {
    "Content-Type": "audio/wav",
  },
  body: file,
});

const transcription = await response.json();
```

Do not use `FormData` or `multipart/form-data` with this endpoint. `MediaRecorder` commonly produces `audio/webm;codecs=opus`, which is not accepted directly; convert it to WAV first.

### Streaming behavior

The endpoint currently expects one complete WAV request. The server buffers the request body before parsing and processing it:

```text
upload complete WAV -> parse and normalize -> transcribe -> JSON response
```

There is no live microphone stream, WebSocket endpoint, partial-transcript endpoint, or incremental audio response yet. HTTP may transport a request in chunks internally, but the transcription pipeline does not process those chunks incrementally.

## `POST /v1/analyze`

Runs the current deterministic `RuleBasedIncidentAnalyzer` against a transcript. It does not call an LLM, save an incident, confirm a report, or execute an action.

There is no combined audio-to-analysis route. A client must call `/v1/transcribe` first and then send the returned text to `/v1/analyze`.

### Request

```bash
curl -i -X POST http://127.0.0.1:8000/v1/analyze \
  -H 'Content-Type: application/json' \
  -d '{
    "transcript": "A vehicle collided with a barrier near the west entrance. Severity is low. Please notify the site supervisor."
  }'
```

Request rules:

- `transcript` is required and must be a string.
- Surrounding whitespace is removed before validation.
- The transcript must be non-empty after trimming.
- The maximum length is 16,000 Unicode characters.
- Unknown JSON fields are rejected.

### Response: `200 OK`

```json
{
  "incident_type": "collision",
  "location": "the west entrance",
  "severity": "low",
  "summary": "A vehicle collided with a barrier near the west entrance. Severity is low. Please notify the site supervisor.",
  "recommended_action": "Please notify the site supervisor"
}
```

The response contains exactly these five string fields:

| Field | Current behavior |
| --- | --- |
| `incident_type` | Simple keyword-based category, or `unknown` |
| `location` | Text following markers such as `near`, `at`, `by`, or `in`, or `unknown` |
| `severity` | Explicit `low`, `medium`, or `high`, or `unknown` |
| `summary` | The trimmed transcript |
| `recommended_action` | Text following markers such as `please`, `notify`, `call`, or `contact`, or `unknown` |

The analyzer only copies explicit facts and uses `unknown` when it cannot extract a field. `recommended_action` is advisory text only. The server does not call anyone, dispatch an emergency, send a notification, or otherwise execute it.

### Analysis errors

| Condition | Status | Response |
| --- | ---: | --- |
| Blank or overlong transcript | `400` | Custom `invalid_request` envelope |
| Analyzer returns an invalid report | `502` | Custom `invalid_model_response` envelope |
| Malformed JSON | `400` | Axum default JSON rejection |
| Missing/non-string/null transcript or unknown field | `422` | Axum default JSON rejection |
| Missing/non-JSON content type | `415` | Axum default JSON rejection |

Custom validation example:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "A non-empty transcript of at most 16000 characters is required."
  }
}
```

The Axum extractor rejection bodies are currently plain text and do not use the custom `error.code`/`error.message` envelope.

## Metrics correlation

The transcription and analysis routes accept these optional headers:

| Header | Behavior |
| --- | --- |
| `X-Run-ID` | Trimmed non-empty value becomes the metrics run ID |
| `X-Experiment-ID` | Optional experiment correlation ID |
| `X-Incident-Active` | Accepts `true`, `1`, `yes`, `false`, `0`, or `no`, case-insensitively |

If `X-Run-ID` is absent, the server generates an ID like:

```text
run_<epoch_milliseconds>_<process_local_counter>
```

These headers affect metrics correlation only. They are not returned as response headers and are not authentication credentials.

Metrics are emitted only when `--metrics-enabled` or `PHEME_VA_METRICS_ENABLED=true` is enabled. Resource metrics additionally require `--resource-sampling` or `PHEME_VA_RESOURCE_SAMPLING=true`.

For `/v1/analyze`, incident-only metrics are active by default unless a valid `X-Incident-Active: false` header overrides them. For `/v1/transcribe`, the startup `--incident-metrics` setting is used unless overridden.

## `GET /v1/metrics/batches`

Returns all currently buffered metric events as a JSON array and removes them from the local in-memory batcher.

### Request

```bash
curl -s http://127.0.0.1:8000/v1/metrics/batches
```

### Response: `200 OK`

```json
[
  {
    "schema_version": 1,
    "experiment_id": "exp-123",
    "run_id": "run-123",
    "sequence_number": 0,
    "timestamp_ms": 1760000000000,
    "events": [
      {
        "schema_version": 1,
        "experiment_id": "exp-123",
        "run_id": "run-123",
        "sequence": 0,
        "timestamp_ms": 1760000000000,
        "name": "end_to_end_request_duration_ms",
        "value": 742.4,
        "unit": "milliseconds",
        "scope": "run",
        "source": "core.workflow"
      }
    ]
  }
]
```

If no events are pending, the response is:

```json
[]
```

### Batch semantics

- Each call drains all events pending at the time of the call.
- Events are grouped by `(experiment_id, run_id)`.
- Events within a batch are sorted by their run-local `sequence`.
- `sequence_number` is assigned by the local batcher and is not a durable cursor.
- Event timestamps are created when events are published; the batch timestamp is created when the batch is drained.
- There are no filters, acknowledgements, retries, or persistence.
- Events are lost if the server restarts or if a consumer drains them and fails before saving/forwarding them.
- A disabled metrics configuration returns `[]` even though the route itself remains available.

Each batch contains:

| Field | Description |
| --- | --- |
| `schema_version` | Current wire schema version, currently `1` |
| `experiment_id` | Optional experiment ID |
| `run_id` | Metrics run ID |
| `sequence_number` | Local batch sequence |
| `timestamp_ms` | Batch creation time in epoch milliseconds |
| `events` | Metric events in sequence order |

Each event contains `schema_version`, optional `experiment_id`, `run_id`, `sequence`, `timestamp_ms`, `name`, `value`, `unit`, `scope`, `source`, and optional `unavailable_reason`.

Metric values are scalar JSON values: numbers, integers, strings, booleans, or `null`. An unavailable measurement is represented by `"value": null` together with `unavailable_reason`; unavailable power, energy, or thermal values must not be interpreted as zero.

## External Go backend forwarding

The Rust server does not know the Go backend URL and does not forward batches automatically. An external host or exporter can:

1. Call `GET /v1/metrics/batches` on the Rust server.
2. Deserialize the returned array.
3. Forward each batch to the Go API's external metrics route:

```http
POST http://127.0.0.1:8080/api/v1/experiments/{experiment_id}/metrics
Content-Type: application/json
```

The Rust drain is destructive, so the exporter should persist or successfully forward returned batches before treating them as delivered. See [`docs/api/metrics.md`](../../../docs/api/metrics.md) for the Go-side contract.

## Current gaps

The following intended capabilities are not registered in this server yet:

- No `/v1/logs` or other HTTP log-retrieval endpoint.
- No structured log persistence or search. TUI logs and process stdout/stderr are separate from this API.
- No `/v1/emergency` or action/dispatch endpoint.
- No emergency detection, notification, escalation, acknowledgement, or cancellation workflow.
- No sessions, clarification turns, corrections, confirmation, report IDs, incident storage, or report retrieval.
- No automatic Rust-to-Go API bridge or metric retry queue.
- No speech-synthesis or audio-response endpoint.
- No model reload or runtime configuration endpoint.

The `recommended_action` returned by `/v1/analyze` is descriptive text only; it does not trigger an emergency operation.

## Testing

From `pheme-va/`:

```bash
cargo fmt --all -- --check
cargo test -p server
cargo test --workspace
cargo clippy -p server --all-targets -- -D warnings
```

Model-backed transcription requires local model weights. A successful endpoint response with a silent WAV verifies the HTTP/WAV pipeline, but it does not validate speech-recognition quality.
